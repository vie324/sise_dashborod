# SalonOne 連携ガイド

ダッシュボードの売上・インセンティブ・目標は、SalonOne の **分析API**（読み取り専用）から取得したデータで計算しています。
このページは「API の接続方法」と「SalonOne のデータをどう集計しているか」をまとめたものです。

API の仕様: <https://salonone.net/api-docs>（schema_version `2026-10-16` に合わせて実装）

---

## 1. 接続手順

1. SalonOne の **ブランド管理 >「API連携」** でアクセスキーを発行する
   - 用途がわかる名前: `社内分析ダッシュボード`
   - 有効期限: 1年（期限が来たら再発行して差し替える）
   - **「サロンワンのログインを必須にする」: チェックを外す**（最初からチェックが入っている。このダッシュボードはサーバーから
     キーだけで読むため、ログイン必須のキーは `401 user_auth_required` になる。一覧では「ログイン必須」と出る）
   - **「カルテ・問診票を含める」: 外す**（カルテは読まない。健康状態を含みうるので不要な権限は付けない）
   - **「個人情報を含める」: 外す**（集計に氏名・電話番号は使わない）。施術ツールのカウンセリングの「本日のお客様」に
     お名前も出したい場合・Google フォームの回答と予約をお名前で結びつけたい場合だけチェックする
     （含めないキーでは顧客番号で選ぶ。[COUNSELING.md](COUNSELING.md)）
   - キーは発行時に一度しか表示されないので、その場で**全体**を控える（一覧の `so_analytics_xxxx…` は先頭だけで、使えない）
2. Vercel > Project > Settings > Environment Variables に登録して **再デプロイ**
   | 変数 | 内容 |
   |---|---|
   | `SALONONE_API_KEY` | 発行したキー（必須。未設定ならデモデータで動く） |
   | `SALONONE_API_BASE_URL` | 既定 `https://salonone.net/api/analytics/v1`。通常は設定不要 |
   | `SALONONE_API_ENDPOINTS` | エンドポイントのパスの上書き（JSON。通常は設定不要） |
   | `SALONONE_RATE_LIMIT_PER_MINUTE` | 1分あたりの呼び出しの上限（既定 55）。SalonOne でキーの上限を上げてもらった時だけ |
3. ダッシュボード > **設定 > SalonOne連携** の「使っているキー」の先頭（`so_analytics_xxxx…`）が SalonOne の一覧の使うキーと同じか確かめ、
   「接続テスト」で各データが取得できるか確認する（SalonOne から取れない時も、この 2つと手順は表示される）
4. 同じ画面で **店舗・スタッフ・来店経由** を対応付けて保存する

キーはサーバーの環境変数にだけ置き、ブラウザ・スタッフの端末には送りません。
リクエストにはヘッダ `X-SalonOne-Api-Key: <キー>` で付けています（`Authorization: Bearer` はユーザー認証のトークン用なので使わない）。

## 2. 取得しているデータ

ベース URL `https://salonone.net/api/analytics/v1` からの相対パスです。

| データ | エンドポイント | 使い道 | 取得の単位 |
|---|---|---|---|
| キーの情報 | `GET /meta` | 接続テスト | — |
| 店舗 | `GET /shops` | 店舗の対応付け（`deleted_at` のある店舗は除く） | 30分ごと |
| スタッフ | `GET /staffs` | スタッフの対応付け・所属店舗（`deleted_at` のあるスタッフは除く） | 30分ごと |
| 流入元 | `GET /visit-sources` | 来店経由 → 集客経路の対応付け | 30分ごと |
| 売上サマリ | `GET /sales/summary?from=&to=&shop_id=` | 入金売上・施術数・新規数・既存（リピート）数・顧客数・契約（購入）数・物販売上。日別・スタッフ別も（SalonOne の売上分析と同じ数字）。消化売上は参考 | 店舗 × 月 |
| 受付履歴の明細 | `GET /marketing/reception-history?from=&to=&shop_id=` | 施術消化売上（来店ごとの消化額・購入したプラン）・経路別の新規・契約（インセンティブ用）・現金売上 | 店舗 × 月（推移では取らない。出納帳の突合・締めはこれだけを取る） |
| 〃（当日分） | `GET /marketing/reception-history?from=今日&to=今日&shop_id=` | 施術ツールのカウンセリングの「本日のお客様」（時刻・状態・担当・媒体・初回か・この来店での契約。「含める」キーなら氏名） | 店舗 × 日（画面を開いている間 1分ごと） |
| 継続管理のサマリー | `GET /marketing/retention-summary?plan_kind=subscription&shop_id=` | 会員数・退会率 | 店舗ごと（当月だけ。毎日 23時台に Cron でも記録） |
| 継続管理の顧客一覧 | `GET /marketing/retention-customers?plan_kind=subscription&shop_id=` | 平均継続期間・都度払いのプランだけのお客様・お客様のプラン（SalonOne の消化額が 0円のサブスクの来店に 1回分を当てる） | 店舗ごと（6時間） |

- 明細（`/shops` など）は `limit=1000` と `meta.next_cursor` で最後まで辿ります
- 受付履歴は `shop_id` が必須のため、店舗ごとに 1ヶ月ずつ取得します（予約日時がその月の予約。キャンセルも含む）
- 日付は店舗のタイムゾーン（日本時間）の暦日です

### 呼び出し回数（1分 60回・1日 20,000回の上限）

- ホーム・インセンティブ・目標・売上分析（月の集計）は、スタッフのインセンティブをヘルプで入った他店舗の実績も含めて
  計算するため、**表示中の店舗のほかに他の店舗も 2段階で取得**します（画面に出す店舗の数字・スタッフは権限の範囲だけ）
  1. 表示中の店舗: 売上サマリ・受付履歴（当月を含む時は継続管理も）
  2. 他の店舗: 売上サマリだけ。そのスタッフ別に、一覧に出すスタッフ（スタッフ本人なら自分。店長以上は所属店舗が表示中の
     店舗の人・所属店舗が対応付いていない人・SalonOne のスタッフ一覧に無い（辞めた）人）がいる店舗だけ、受付履歴も取る。
     取れなかった時は「ヘルプで入った分が入っていない可能性があります」と注意を出す（確定の前の確認にも出る）
- 推移（6ヶ月）は表示中の店舗の売上サマリだけ。スタッフ本人の推移（自己ベスト）は他の店舗の売上サマリも取る
- インセンティブの確定は、支給期間のすべての月で **10分より前に取得したもの**を取り直す（直前に開いた画面の分は使い回す。
  上限に当たって取り直せなかった分は、確認の後の「このまま確定する」でもう一度取りに行く）
- 出納帳（突合・レジ金チェック・日次締め・取り込み）は、その店舗の受付履歴だけ（1ヶ月 1回）
- 当月は 5分、前月は 30分、それより前の月は 6時間、メモリにキャッシュします（本日のお客様は 50秒）
- 同時に 4本まで、1分 55回までに抑えます。上限に当たったら 1回だけ待って取り直し、それでもだめなら前回の値を表示します

目安: 受付履歴は 1ページ 1,000件なので、ふつうは 店舗 × 月 で 1回。3店舗のブランドで、ホームを開くと最初の 1回は 20〜30回ほど、
確定は 店舗数 × 6 + 3 回ほど。以降はキャッシュから返します。

## 3. うまくつながらないとき

設定 > SalonOne連携 >「接続テスト」で、各エンドポイントの結果と項目名が出ます（金額・顧客などの値は出しません）。
あわせて、次の 3つを数字の確認用に出します（顧客の情報は含みません）。

- **継続管理の人数**（継続 / 要フォロー / 要注意 / 離反 と 1か月前）→ SalonOne の マーケティング > 継続管理（サブスク）の画面と同じか
- **受付履歴の値の種類と扱い**（状態・キャンセル区分・区分・プラン種別・決済方法）→ 例: `completed → 会計完了（集計する）`、
  `現金 → 現金`。「不明（集計しない）」がある・現金の決済方法が「現金以外」になっている場合は、`api/_lib/salonone/normalize.js` を直す
- **継続管理の顧客一覧の値と扱い**（顧客の状態・プラン名）→ プラン名が「都度払い（このプランだけのお客様は会員数・平均継続期間から除く）」に
  なるのが都度払いのプランだけか（設定 > SalonOne連携 > プランの判定 のキーワード）。どちらも最初のページ（1,000件まで）の値

「結果をコピー」で開発担当に共有できます。

| 表示 | 原因と対処 |
|---|---|
| APIキーが無効です（401 `unauthorized`） | キーの入力ミス・途中で切れている・失効済み・期限切れ。設定の「使っているキー」の先頭を SalonOne の一覧と見比べる。違えば本番（Production）の `SALONONE_API_KEY` が差し替わっていない（差し替えて Redeploy）。同じなら、そのキーが失効済みでないか・貼った値が途中で切れていないか。直らなければ再発行して差し替える |
| ログインを必須にする（401 `user_auth_required`） | 「サロンワンのログインを必須にする」のチェックを外したキーを発行し直す（一覧で「ログイン必須」が付いていないキー） |
| キーに使えない文字（`invalid_key`） | `SALONONE_API_KEY` に「…」や全角文字が入っている（一覧の先頭だけをコピーした など）。発行時に表示された全体を貼り直す。前後の空白・改行・引用符・`SALONONE_API_KEY=` は自動で外す |
| 取得できない範囲（403 `forbidden` / `feature_disabled`） | 他ブランドの店舗を指定している、またはブランドで機能（マーケティング・継続管理）が無効 |
| 為替レートが未登録（`exchange_rate_not_set`） | 外貨の店舗がある場合、SalonOne の為替レート設定で登録 |
| 利用上限（429 `rate_limited`） | 1分ほど待ってから ⟳。頻繁に出る場合は SalonOne にキーの上限を相談し、`SALONONE_RATE_LIMIT_PER_MINUTE` を合わせる |
| SalonOne 側でエラー（500 `internal_error`） | 時間をおいて再度。続く場合は表示された `error_id` を SalonOne の運営に伝える |

エラーの詳細（顧客の情報）は SalonOne 側が返さない仕様です。問い合わせには `error_id` を使います。

項目名が変わった場合は `api/_lib/salonone/normalize.js` の候補リストに追加し、`test/normalize.test.js` を更新します。
ローカルでは疑似 SalonOne（`scripts/dev/salonone-fake.mjs`）でライブの経路を試せます:

```sh
node scripts/dev/salonone-fake.mjs --port 4100
SALONONE_API_KEY=test-key SALONONE_API_BASE_URL=http://127.0.0.1:4100/api/analytics/v1 npm run dev:local
```

## 4. 集計ルール

すべて `shared/metrics.js`（集計）と `shared/incentive.js`（インセンティブ）で計算しています。サーバーとブラウザで同じコードです。

**入金売上・施術数・新規数・既存数・顧客数・契約数は、SalonOne の売上分析（`/sales/summary`）の数字をそのまま使います。
施術消化売上は、受付履歴から「施術 1回分の金額」を合計します（2026年11月から。§4.1）。**
SalonOne 側は「明細から自前で合計すると数字がずれる（サブスク課金行・プリペイドの二重計上の排除や失効益があるため）」としているため、
店舗・日別・スタッフ別とも売上分析の値を正にしています。

| 画面の指標 | SalonOne の売上分析 | 定義（SalonOne の説明） |
|---|---|---|
| 施術消化売上 | （受付履歴から計算。§4.1） | 施術 1回分の金額の合計 − 物販売上 `product_sales`。参考に SalonOne の消化売上 `consumed_sales`（会計金額に回数券・サブスクの消化分と失効分を加え、前受にあたる回数券・回数ありサブスクの購入額を差し引いた金額）も画面に出す |
| 入金売上 | 入金売上 `digest_sales` | 会計が確定した金額からプリペイド利用分を差し引き、プリペイド入金・キャンセル料を加え、返金を差し引いた金額 |
| 施術数 | 施術数 `treatment_count`（無ければ 新規 + リピート） | 施術を行った件数 |
| 新規数 | 新規数 `new_visit_count` | 店舗ごとに、そのお客様の最初の来店 |
| 既存数 | リピート数 `repeat_visit_count` | 2回目以降の来店 |
| 顧客数 | 顧客数 `customer_count` | 期間中に来店したお客様の実人数 |
| 契約数 | 購入数 `purchase_count` | 新規のお客様のうち、回数券・サブスクを契約した件数（生涯基準。後の月の契約で増える） |

### 4.1 施術消化売上（施術 1回分の金額。オーナー決定 2026-11）

施術した日に、施術した担当スタッフへ「その施術 1回分の金額」を計上します（`shared/consumption.js`）。

| 来店 | 施術消化売上 |
|---|---|
| 都度払い・初回体験 | その来店で払った施術代（例: 初回 3,000円。同時に買ったサブスク 15,000円は入金売上だけ） |
| サブスク | 月額 ÷ 月の回数（例: 月2回 15,000円 → 1回 7,500円） |
| 回数券 | 購入額 ÷ 回数 |
| 含めない | プランの購入・毎月のサブスク課金そのもの（入金売上）、使わなかった回・失効、物販、キャンセル料 |

計算のしかた:

- 受付履歴の会計完了の来店ごとの「消化額」（`consumed_amount`）を使う
- **サブスクの来店の消化額は、SalonOne の登録の都合で 0円の時と 1回分（7,500円）の時がある。** 0円の来店（プランの購入も無いもの）は、
  そのお客様のプラン（継続管理の顧客一覧・受付履歴での購入）の 1回分の金額を当てる
- プランの 1回分の金額は、次の順で決める（設定 > SalonOne連携 > **プランの 1回分の金額** で確かめられる）
  1. 設定で入れた金額
  2. 同じプランだけを持つお客様の来店で、SalonOne が消化額を付けたもの（いちばん多い金額）
  3. 購入額 ÷ 回数（サブスクはプラン名の「月2回」「月一」「週1回」など、回数券は回数）
- 1回分の金額が決まらないプランの来店は施術消化売上に入らない。画面と確定の前の確認に「1回分の金額がわからないプランの来店」と出るので、設定で金額を入れる
- サブスクを買った来店で、SalonOne が購入額まで消化額に入れている（会計金額の全額が消化額）時は購入額を外す
- SalonOne の区分「サブスク課金」の行（来店ではない）は数えない
- 物販は来店ごとに分けられないため、月の合計から売上分析の物販売上（`product_sales`）を差し引く。
  既存顧客の消化売上・初回来店の消化額は、初回来店とそれ以外の比で物販を分けて差し引く
- 日別のグラフは受付履歴の日別の形のまま、月の合計（物販を差し引いた金額）に合わせる

**推移のグラフ**は毎月の受付履歴を取らずに済むよう、月ごとの施術消化売上の記録（`dash_config` の `incentive.consumption`。
店舗・スタッフごと。スタッフの金額を含むので一般の設定 API からは読めない）を使います。記録は、その月（と前の月）の画面を開いた時と、
毎日の Cron（当月・月初の 5日は前月・記録の無い過去の月を 1つずつ。直近 12ヶ月）で残ります。
記録の無い月は SalonOne の売上分析の消化売上で埋め、グラフに注記を出します（自己ベストでは比べない）。

**スタッフのインセンティブは、表示中の店舗にかかわらず全店舗の実績で計算します**（ヘルプで他店舗に入った分も含める。
売上分析のスタッフ別を店舗ごとに合計した値）。店舗を絞った時・スタッフ本人が見た時・オーナーが全店舗で見た時で金額は同じです。

- インセンティブ・目標・ランキングのスタッフの一覧は、**所属店舗**（SalonOne のスタッフの所属店舗。ダッシュボードの店舗と
  対応付いていなければ、支給期間に最後に施術した店舗）で出す。支給期間のどちらの月を開いても同じ店舗になる
- 支給期間の途中で辞めた人（SalonOne のスタッフ一覧に無い人）も、期間内に実績があれば一覧・期間の合計・確定に入る
- 売上分析のスタッフ別は、**表示中の店舗での実績**（SalonOne の売上分析で店舗を絞った時と同じ）。ヘルプのスタッフには「ヘルプ」と出す
- 継続率インセンティブは月ごとに所属店舗の条件で判定する（所属店舗が対応付いていない人は、その月にいちばん施術した店舗。
  辞めた人は施術のある月だけ）。施術の無いスタッフも所属店舗が条件を満たせば対象（確定の前に名前を出して確認する）
- ダッシュボードの店舗と対応付いていない SalonOne の店舗に実績がある時は、管理者に注意を出す（その店舗だけで施術した
  スタッフは所属店舗が無いので一覧・確定に入らない。新しい店舗の対応付け忘れに気づけるように）

インセンティブの経路別の判定は、受付履歴（`/marketing/reception-history`）から集計します。

| 指標 | 計算方法（受付履歴の項目） |
|---|---|
| 経路別の新規 | その店舗で初めての会計完了の来店（区分 `classification=new` の予約。最初の予約をキャンセルして後日来店した場合はその来店）。担当はその来店のスタッフ、経路は `visit_source_name` |
| 経路別の契約 | 上の新規のお客様が、回数券・サブスクを購入（`plans[].plan_kind`）または入会（`joined`）した件数。初回来店の月に計上し、基準日までの契約を数える（後の 2ヶ月の受付履歴まで見る） |
| 既存顧客の消化売上 | 施術消化売上（§4.1）から、新規のお客様の初回来店の施術 1回分を差し引いた金額 |
| 現金売上 | 会計完了の予約のうち現金で受け取った額。分割決済（`payment_splits`）は現金の分だけ。決済方法が「現金 / クレジットカード」のように複数なのに内訳が無い行は、現金の分がわからないので数えない（カードの分までレジに入ったことにしない。出納帳に件数と金額を出す） |
| 経路 | 来店経由を「ホットペッパー / Meta広告 / ホームページ / Minimo / Threads / Instagram / 紹介 / その他」に対応付け（未設定は名前から推定） |
| 紹介 | 経路が「紹介」の新規のお客様がサブスク（シェアプラン除く）を契約した件数。担当スタッフに計上 |
| 契約の担当 | 新規のお客様が 2回目以降の来店で別のスタッフのもとで契約した時も、**初回来店の担当**の契約として数える（契約率の分母・分子を同じスタッフにそろえる。オーナー決定 2026-10） |
| 系列店での契約 | 来店した店舗とは別の系列店（ドミナント出店）で契約したお客様。店長以上がこのシステムで登録すると、初回の店舗のスタッフに 1件 2,000円。契約した店舗の SalonOne の契約を選んで登録した分は、その店舗の担当の新規契約（3経路・SNS・紹介）から除く（二重に数えない。SalonOne の購入数＝画面の契約数はそのまま）。§5.5 |

経路別の合計は、SalonOne の「既存顧客として扱う」にしたお客様などの扱いの違いで、新規数と少しずれることがあります（売上分析の画面に注記を出します）。

売上分析の「新規の内訳と媒体別の契約率」（`shared/newBreakdown.js`。ホームの新規数のタイルからも開ける）は、上の経路別の新規・契約を媒体（経路）ごとに並べたもの:

- 新規の内訳: 媒体ごとの新規数と構成比（新規の多い順。3経路は 0名でも出す）。「その他」などに入った来店経由の名前を横に出す
- 媒体別の契約率: 契約数 ÷ 新規数。縦線は全体の契約率。先頭の「3経路の合計」は新規契約インセンティブの判定と同じ契約率
- 来店経由ごと: SalonOne の来店経由の名前のまま、新規・契約・契約率（どの媒体にまとめたか）
- 2回目以降の来店での契約も初回来店の月に数えるため、月の契約率は後から上がることがある

継続指標は SalonOne の継続管理（サブスク）から:

| 指標 | 計算方法 |
|---|---|
| 会員数 | 継続管理（サブスク）の 正常 + 要フォロー + 要注意 の人数（離反以外）。取得時点。プラン名が「都度払い」のキーワード（設定 > SalonOne連携 > プランの判定）に当たるサブスクだけのお客様（顧客一覧で離反以外）は除く |
| 退会率 | 直近 1か月に離反へ移った人数 ÷ 1か月前の会員数（継続管理の `previous_month` との差） |
| 平均継続期間 | 直近 1年にサブスクの支払いがあったお客様の、サブスク継続月数（`subscription_months`）の平均。お客様ごとに数える（複数のプランがあれば最も長いもの）。都度払いのプランだけのお客様は除く |

インセンティブ制度（金額・閾値）は `shared/incentive-rules.js` にまとまっています。
資料の「既存顧客の施術消化売上が月間 40,0000円以上」は **400,000円** と解釈しています。

### 会員数・退会率は「取得した時点」の値（毎日 23時台に記録）

SalonOne の継続管理は取得した時点の状態しか返さないため、`dash_config` の
`salonone.retentionSnapshots`（`{ 'YYYY-MM': { [SalonOne店舗ID]: 継続指標 } }`、24ヶ月分）に記録し、
過去の月は**その月の最後の記録**を使います。連携より前の月は記録が無いため「—」と表示します。

- **Vercel Cron が毎日 23時台（JST）に全店舗の継続管理を取り直して記録**します（`vercel.json` の `crons`・`/api/salonone?action=cron`）。
  月の最後の日の 23時台の記録が、その月の会員数・退会率（継続率インセンティブの判定）になります
- 画面で当月を開いた時にも記録します（Cron が動かなかった日も、開いた時点の値が残る）
- 退会率の「1か月前」は取得した日の 1か月前なので、月末に記録した値がその月の退会率になります
- 画面には「◯/◯時点の SalonOne の継続管理」と出します（インセンティブの継続率のカード・ホームのチームの状況）
- Cron は環境変数 `CRON_SECRET` を設定すると、Vercel が `Authorization: Bearer <CRON_SECRET>` を付けて呼びます。
  `REQUIRE_ADMIN_AUTH=true` の場合は `CRON_SECRET` が無いと Cron が 401 になり記録されません（RUNBOOK §1）
- 手で記録し直す: 管理者ログインした状態で `/api/salonone?action=cron` を開く（続けて動かせるのは 10分に 1回）
- 1店舗も記録できなかった時は 502 を返す（Vercel > Cron Jobs の記録で失敗に見える）。一部の店舗だけ失敗した時は 200 で `failed` に出す
- 記録は `dash_config` の 1行を読み直して書き戻すため、Cron と画面の記録が同じ瞬間に重なると、片方の店舗の値がその日だけ
  残らないことがある。月の最後の日に起きると前の日の記録がその月の値になるが、確定の前の確認（月末の記録ではない）に出る

## 5. インセンティブの確定（支給期間ごと）

契約数は SalonOne の購入数と同じ「生涯基準」（後の月の契約で前の月の契約数が増える）、会員数・退会率は「取得した時点」の値なので、
**支給した後に画面を開き直すと金額が変わることがあります**。支給期間（2ヶ月）が終わったら、オーナー（管理者）が金額を確定して固定します。

1. 支給期間が終わったら（例: 11〜12月の分は 1月に入ってから）、インセンティブ > スタッフ別 で期間の最後の月（12月）を開く
2. 「確定する」→ 10分より前に取得したデータを SalonOne から読み直して計算し、確認してほしいことがあれば表示する
   - 取得できなかったデータ・前回の値の表示・他の店舗の実績の一部が取れなかった（時間をおいてやり直す）
   - 会員数・退会率の記録が無い月（継続率インセンティブが 0円で確定される）
   - 会員数・退会率が月末の記録ではない月（◯/◯時点の値で確定される。Cron が月末に動かなかった）
   - 施術の無い月にも継続率インセンティブが入っているスタッフ（所属店舗のスタッフとして支給してよいか）
   - ダッシュボードの店舗と対応付いていない SalonOne の店舗に実績がある・店舗の対応付けの重複
   - ダッシュボードのスタッフと未連携の SalonOne スタッフに支給額がある
   - 系列店での契約のうち、契約した店舗の SalonOne の契約と結びついていないもの（その店舗の契約数を減らしていない）
3. 確定すると、ホーム・インセンティブの「支給期間の合計」が確定した金額になる（スタッフ本人にも「確定」と出る）。
   確定した後に SalonOne の数字が変わった場合は「再計算」の金額を並べて出す（支給額は変わらない）。
   確定した記録に入っていないスタッフは「—（確定の記録なし）」と出し、合計には入れない（取り消して確定し直すか確かめる）
4. 「CSV」で支給一覧（スタッフ × 月の内訳・判定に使った数字・会員数の記録日・支給額）をダウンロードできる（店長以上。確定前は「見込み」）
5. やり直す時は「確定を取り消す」→ もう一度「確定する」（前の記録は履歴として 10件まで残る）

- 確定した日までの契約を数える（確定後に入った契約は数えない）
- 記録は `dash_config` の `incentive.close.<期の最初の月>`。`/api/db` の dashConfig からは読み書きできない
  （スタッフには自分の分だけ・メモなし、店長以上には表示中の店舗のスタッフの分だけを返す）
- 記録には月ごとに、判定に使った数字・施術数・継続指標を見た店舗（`retentionShopId`）と記録日（`retentionAsOf`）も残す
- 実装: `api/_lib/salonone/summary.js`（`closePeriod` / `reopenPeriod`）・`closes.js`、`src/features/incentives/PeriodClose.jsx`、`shared/incentive.js`（`incentiveCsv`）

### 5.5 系列店での契約（ドミナント出店）

来店したお客様が系列の他店舗で契約した場合、SalonOne では契約した店舗の契約になります。
店長以上が インセンティブ > スタッフ別 の「系列店での契約」から登録すると、初回に来店した店舗のスタッフに 1件 2,000円
（`INCENTIVE_RULES.crossStore`）が付きます。

1. 「登録する」→ 契約日と契約した店舗を選ぶと、その日の SalonOne の契約（会計完了でサブスク・回数券の購入か入会のある受付）が出る
2. 該当の契約を選ぶ（プラン名が入る）。選んだ契約は、契約した店舗の担当の新規契約から除く。見つからない時は「選ばない」で登録できる
   （契約数は減らさない。確定の前に「結びついていない登録」として確認を求める）
3. お客様名・プラン名・2,000円を付けるスタッフ（初回に来店した店舗の担当）を入れて登録

- 契約日の月のインセンティブになる。確定した支給期間の月は登録・削除できない（確定を取り消してから）
- 登録・削除: オーナー・管理者と、2,000円を付けるスタッフの所属店舗の店長・マネージャー。
  一覧はスタッフ本人（自分の分）・その店舗か契約した店舗の店長以上が見られる
- 初回の店舗と同じ店舗での契約は対象外（SalonOne の新規契約として数える）。同じ SalonOne の契約は 2回登録できない
- 契約した店舗が担当店舗でない時は、SalonOne の契約にお客様の名前を出さない（顧客番号・時刻・担当・プランで選ぶ）
- 記録は `dash_config` の `incentive.cross.<契約日の月>`（削除した登録も 20件まで残す）。`/api/db` の dashConfig からは読み書きできない
- 実装: `api/_lib/salonone/cross.js`・`cross-handlers.js`、`shared/metrics.js`（`excludedContracts`）、`src/features/incentives/CrossStore.jsx`

## 6. 出納帳への現金売上の取り込み

出納帳（Supabase）は SalonOne に書き込めない（分析API は読み取り専用）ため、SalonOne → 出納帳 の向きでつなぐ。

- 受付履歴の現金売上（上の「現金売上」）を、店舗・日ごとに合計（`cashSales`）
- 出納帳 > SalonOne突合 / 日次締め / レジ金チェック から取り込むと、1日 1件の入金（レジ・現金・施術売上）になる
- 記録の ID は `so_<店舗ID>_<日付>` で固定。何度取り込んでも 1件で、SalonOne の金額が変わっていれば更新する
- 取り込まない日: SalonOne の集計日より後 / 締め済み / 手入力の現金売上がある（二重計上を避ける）
- 取り込む金額は常に SalonOne から読み直す（当月・前月。受付履歴だけを取るので 1ヶ月 1回の呼び出し）
- **レジ金チェック・日次締めのダイアログは、開くたびに本日の現金売上を SalonOne から読み直し**、確定の前に必ず取り込み直す
  （数分前の金額で理論残高を出すと、取り込んだ後の現金の会計が「差異」としてその他収入に記録されてしまうため。
  金額が同じならサーバーは何もしない）。SalonOne の金額を確かめている間は確定できない
- SalonOne につながらない時は、ダイアログに注意を出す（締めた日は後から取り込めない）
- 「現金 / クレジットカード」のように複数の決済方法で内訳が無い会計は、現金の分がわからないので取り込む金額に入れない。
  件数と会計金額を SalonOne突合・レジ金チェック・日次締めに出す（SalonOne の会計で決済の内訳を登録すると、次に開いた時から現金の分が入る）
- デモデータは取り込まない

実装: `api/_lib/db-handlers-cashbook.js`（`importSalonOneCash`）、`shared/cashbook.js`、`src/features/cashbook/`。

## 8. キャッシュ

サーバーレス関数のメモリに、当月の売上サマリ・受付履歴は 5分、前月は 30分、それより前は 6時間、店舗・スタッフは 30分、
継続管理の人数は 30分、平均継続期間は 6時間キャッシュします。
取り直しに失敗したときは前回の値を表示し、画面に「◯時◯分時点のデータを表示しています」と出します。
画面の更新ボタン（⟳）と 設定 > SalonOne連携 >「データを取り直す」で取り直せます（⟳ で取り直すのは当月と前月だけ）。

## 9. 運用開始前の確認（2026年11月〜）

数字の計算はテストで確かめていますが、**SalonOne の実データでしか確かめられない前提**があります。10月の数字で次を確認してから運用を始めてください。

| # | 確認すること | 見る場所 | 合わない時 |
|---|---|---|---|
| 1 | 施術消化売上（§4.1）が施術 1回分で数えられている: 設定 > SalonOne連携 > プランの 1回分の金額 で、各プランの自動の金額（月2回 15,000円 → 7,500円 など）が正しく、「わからない来店」が無い | 設定 > SalonOne連携 > プランの 1回分の金額、売上分析 > スタッフ別 | 違うプラン・決まらないプランに金額を入れて保存する |
| 2 | 会員数が、SalonOne の マーケティング > 継続管理（サブスク）の 継続 + 要フォロー + 要注意 と同じ。SalonOne の「継続顧客数」がすでに要フォロー・要注意を含んでいないか | 設定 > SalonOne連携 > 接続テスト の「継続管理のサマリー」、ホームの会員数 | 含んでいる場合は会員数が多く出るので開発担当に連絡（`normalizeRetention`） |
| 3 | 受付履歴の「状態」に「不明（集計しない）」が無い。現金の決済方法が「現金」と判定されている | 接続テスト の「受付履歴の明細」 | `normalize.js` の `STATUS_MAP`・`CASH` に足す |
| 4 | 来店経由がすべて正しい経路（3経路・SNS・紹介）に対応付いている | 設定 > SalonOne連携 > 来店経由 → 集客経路 | 対応付けを保存 |
| 5 | 全スタッフが SalonOne のスタッフと対応付いている（未連携のバッジが無い）・所属店舗が正しい | インセンティブ > スタッフ別 | 設定 > SalonOne連携 > スタッフの対応付け、SalonOne のスタッフの所属店舗 |
| 6 | 「入会（プラン種別なし）」を新規契約に数えてよいか（紹介インセンティブはサブスクのプランがある時だけ） | 売上分析 > 新規の内訳と媒体別の契約率 | 数えない場合は開発担当に連絡（`contractsFromReceptions`） |
| 7 | Vercel の Cron（毎日 23時台）が動いている | Vercel > Project > Cron Jobs のログ、ホームの「◯/◯時点の SalonOne の継続管理」 | `CRON_SECRET` を設定して再デプロイ |
| 8 | 出納帳の SalonOne突合で、10月の現金売上が実際のレジと合う | 出納帳 > SalonOne突合 | 差異のある日の会計（分割決済・返金・キャンセル料・現金のサブスク課金）を確認。「現金の分がわからない会計」が出たら SalonOne で決済の内訳を登録する |
| 9 | 都度払いのプランだけが「都度払い」と判定されている | 接続テスト の「継続管理の顧客一覧」のプラン名 | 設定 > SalonOne連携 > プランの判定 のキーワードを直す |
| 10 | 「対応付いていない SalonOne の店舗に実績があります」が出ていない | ホーム（管理者） | 設定 > SalonOne連携 で店舗を対応付ける（使わない店舗なら SalonOne 側で削除済みにする） |

**現金売上に入らないもの**: 返金（現金で返した分）、キャンセル料、プリペイドの入金、予約に結びつかないサブスク課金は、受付履歴の会計完了の行に無いため取り込まれません。
現金で受け渡しがある場合は、出納帳に手で記録してください（「施術売上」など売上のカテゴリで手入力するとその日の取り込みが止まるので、「その他収入」「その他経費」で記録する）。
